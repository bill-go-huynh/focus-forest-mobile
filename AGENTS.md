# focus-forest-mobile — Agent Instructions

The Focus Forest consumer app: **React Native + Expo + TypeScript**.

Workspace rules in `../AGENTS.md` also apply. These repo rules govern implementation details. They never override product behavior (`../focus_forest_product_features.md` plus the confirmed decisions listed in `../docs/README.md`). If a constraint here conflicts with product behavior, flag it. Shared docs live in `../docs/`. If this repo is checked out on its own without the workspace, ask for the docs before making product or design decisions.

## Responsibilities

- All consumer UI across the full product: onboarding, Home, timer, session completion, history, tree details, forest, insights, recap, profile, settings, achievements, collection, species and cosmetics, social (Together tab), Focus Together, challenges, events, Community Tree, leaderboards, seasonal content
- **Tree rendering and all animation**: the core renderer first, then the advanced renderer (`../docs/03_TREE_SYSTEM.md` §8)
- The local timer (accurate through backgrounding, lock, and restart) and the offline session queue
- Accessibility adaptations (text scaling, reduced motion, screen reader descriptions)

## Not responsible for

- Deciding product truth: whether a session counts, growth, stage, vitality, streaks, rest-day validity, goal completion, rewards, event and challenge progress, month boundaries. Never hardcode tunable values such as the session minimum or thresholds. **Display what the API returns.** Optimistic previews are allowed only as described in `07_API_BOUNDARIES.md` §4.

## Rules

- **Test first** (`../AGENTS.md` → Test-first development). Here that means Jest (`jest-expo`) with React Native Testing Library, in `__tests__/` folders or `*.test.ts(x)` files, never inside `src/app/` (every file there is a route). Priorities: timer accuracy (background, lock, kill and restart) with fake timers, the offline session queue (queueing, retry, no duplicates), rendering what the API returns (including unknown content identifiers and never-dead tree states), accessibility labels and roles, and reduced-motion behavior. Mock the API at the network boundary; never re-implement product rules in tests or code.
- **Tokens only.** No arbitrary colors, spacing, radii, font sizes, shadows, opacities, or durations. If a token is missing, add it to the theme **and** document it in `01_DESIGN_SYSTEM.md`. Tree and scene art uses species and asset palettes, not UI tokens.
- **Reuse components.** Build screens from the shared primitives. Extend with variants instead of making near-duplicates.
- **The tree is the hero.** On Home it is the focal point. It is never a thumbnail in a stats grid. No generic dashboards.
- **Animation restraint.** Calm, meaningful, interruptible, and reduced-motion-aware. No celebrations during focus. No confetti, pulsing, or shaking.
- **Never render a dead, wilted, or damaged tree.**
- **Accessibility is part of done:** 44pt targets, AA contrast, dynamic type up to 200%, labels, tree descriptions.
- **Both themes.** Every screen must work in light and dark mode.
- **Unknown content identifiers** (species, traits) from the API get a graceful fallback, never a crash.
- **Timer reliability beats everything.** Never lose a user's session.
- Follow the documented navigation: 4 tabs, with Together (the community hub) added in Phase 11, and Focus as a full-screen flow. Tabs and Together sections appear only with the phase that fills them.
- The core tree renderer uses authored fixed slots. Don't build a generalized anchor engine before Phase 8–9 (`../docs/03_TREE_SYSTEM.md` §8).
- **Build the current phase only** (`../docs/12_PRODUCT_IMPLEMENTATION_PLAN.md`). Later phases are planned scope, but don't implement them early. Structure code so they can be added without rewrites.

## Tooling

- Expo SDK 57, Expo Router (file-based routes in `src/app/`; keep non-route code outside it), TypeScript strict, npm.
- **Add packages with `npx expo install <pkg>`** so versions match the SDK. Dependency rules: `../AGENTS.md` → Dependencies and supply-chain security.
- Expo APIs change every SDK. Check the versioned docs (`https://docs.expo.dev/versions/v57.0.0/`) instead of relying on memory.
- `ios/` and `android/` are generated (Continuous Native Generation). Configure native behavior in `app.json` and config plugins, never by hand.
- **Theme** (`src/theme/`): read tokens with `useTheme()`. The theme follows the system color scheme. Values are provisional until Phase 0 (`themeValueStatus`), and `src/theme/__tests__/tokens.test.ts` checks AA contrast for every text/surface pair. A lint rule rejects hardcoded colors, spacing, radii, font sizes and weights, line heights, opacity, z-index, shadows, and durations outside `src/theme/`.
- **Accessibility** (`src/accessibility/`):
  - `useReducedMotion()` is true when the system **or** the in-app setting reduces motion. `AccessibilityProvider`'s `appReducedMotion` prop takes the in-app setting and is connected to the API preferences in M13.
  - `useFontScale()` tells layouts when text is at 200% or more, so they can adapt.
  - `touchTargetHitSlop()` and `MIN_TOUCH_TARGET` give every interactive element a hit area of at least 44×44.
  - `announce()` says every motion- or haptic-signaled outcome as text.
  - A lint rule rejects `allowFontScaling={false}` and `maxFontSizeMultiplier` below 2.
- **Components** (`src/components/`): `Button` (`variant` is `primary`, `secondary`, or `tertiary`), `IconButton` (requires `accessibilityLabel`; the icon is drawn through `icon({ color, size })`), and `DestructiveButton` (only `onRequestConfirm`, never `onPress`: the destructive action runs only after a confirmation step). `Card` (static, or tappable with a required `accessibilityLabel`), `ListRow` (`title`, `subtitle`, `meta`, `leading` icon; either `onPress` or a trailing `action`, never both), and `Chip` (`label` is always required, `selected`, optional `topicColor` from `topic.1`–`topic.12` and `icon`). `Input` (`label`, `value`, `onChangeText`, `helper`, `error`, `disabled`, `multiline`, common `TextInput` settings, and a `ref` with `focus()`/`blur()`, ready for a form library `Controller`). `Sheet`, `Modal`, and `Confirmation` share `Overlay` (internal): the parent owns `visible`, each takes `onRequestClose` or `onCancel`, and `returnFocusRef` (every button forwards `ref`) returns screen-reader focus to the opener. `ProgressRing` (`progress` 0–100, clamped; `label` and `valueText` are required and always shown; `tone` is `forest` or `accent`, never red; drawn with `react-native-svg`). `InlineStatus` (`tone` is `neutral`, `info`, or `attention`; `message`, optional `detail` and one tertiary `action`; read as one element with the action separately focusable; each tone has its own glyph and the text stays `text.primary`, so color never carries the meaning; `live` announces it when it appears or its wording changes; calm-copy checked; the action moves under the text at 200%): the inline status for pending sync, saved or cached data, and things that need a look. It takes presentation props only: callers map queue or outbox states to a tone and copy. `TopicMark` (`color` and `icon` as the API sends them, `size` from the icon tokens) draws a topic's line icon in its topic color, hidden from screen readers since the name beside it is read; it is a placeholder glyph for every identifier (`topicMarkStatus`) until the curated icon set exists, and an unknown color or icon falls back instead of failing. `topicColorKey('topic.3')` gives the theme key for `Chip`'s `topicColor`. State components: `EmptyState` (`illustration`, one-sentence `message`, at most one `action`), `ErrorState` (`message`, `reassurance`, `onRetry`, `retryLabel`), and `Skeleton` / `SkeletonGroup`. Spot illustrations (`src/components/illustrations.tsx`) are placeholders until Phase 0 art. State copy is checked by `assertCalmCopy`. Navigation: `src/app/(tabs)/` holds the four tabs in the order set by `src/navigation/tabs.ts`, drawn by `TabBar`; Settings is `src/app/(tabs)/profile/settings.tsx` (depth 2). `Screen` wraps every screen (heading, gutter, scroll). Route tests use `appRoutes` (`src/test-utils/routes.ts`) with `renderRouter`, and `route-structure.test.ts` enforces the tab list and the three-level depth limit. API layer (`src/api/`): `createApi` wires `createHttp` (JSON, timeout, error kinds), `SessionStore` (tokens in memory, persisted by `secureTokenStore` in expo-secure-store; single-flight refresh), `createApiClient` (Bearer header, proactive refresh, one refresh and one retry on 401, clears the session when renewal fails), and `createAuth` (`signUp`, `signIn`, `restoreSession`, `signOut`, on the A3 endpoints). `ApiProvider` supplies it with the TanStack Query client (`createQueryClient`: retries only network and 5xx errors) and drops the query cache on sign-out; read it with `useApi()` and `useSession()`. Errors carry a `kind`: `network`, `unauthenticated`, `http`, `invalid-response`, `configuration`. Never log tokens; lint blocks AsyncStorage in `src/api/`. The base URL comes from `EXPO_PUBLIC_API_URL` (`.env.example`). Auth (`src/auth/`, routes `src/app/(auth)/`): the root layout restores the session once at launch, shows a plain `launch-screen` while the status is `unknown`, then uses `Stack.Protected` to show `(tabs)` only when signed in and `(auth)` otherwise. `useSignUp` creates the account, then sends one `PATCH /me/profile` with the display name and `getDeviceTimeZone()`; `AuthFlowProvider` keeps the auth screens up until that finishes, and `retryProfile` repeats only the profile step. Form errors go through `describeAuthError`, which shows only known API messages. Profile (`src/profile/`, routes `src/app/(tabs)/profile/index.tsx` and `edit.tsx`): `useProfile` (GET `/me/profile`) and `useUpdateProfile` (PATCH, updates the cache); `profileFormSchema` mirrors A4 (a set name cannot be cleared; bio up to 160, blank clears it); `profileChanges` sends only changed fields; `Avatar` draws initials (`initialsOf`) or a seed. Preferences (`src/preferences/`, route `src/app/(tabs)/profile/settings.tsx`): `usePreferences` (GET `/me/preferences`) and `useUpdatePreferences` (PATCH one change at a time: optimistic, serial via a mutation scope, only the last answer replaces the cache, failed saves restore just their fields). `AppearanceProviders` feeds the theme (`ThemeProvider preference`) and `reducedMotion` (`AccessibilityProvider appReducedMotion`) app-wide; the root layout keeps the launch screen on top until a signed-in user's preferences arrive (one failed read stops the wait). Notification categories appear only once their phase exists (`visibleNotificationCategories`, `CURRENT_PHASE`); Phase 1 shows none. `SwitchRow` is the on/off setting primitive. Route tests render with `renderApp` (`src/test-utils/render-app.ts`: `renderRouter`, then real timers, since `renderRouter` leaves fake timers on) and start signed in with `src/test-utils/secure-store-mock.ts`. Tappable primitives share `PressableSurface` (internal). Tests with overlays use `mockControlledTiming` (`src/test-utils/animation.ts`) and `createNodeMock` for focus checks. Test components with `renderWithProviders` (`src/test-utils/render.tsx`).
- **Timer engine** (`src/timer/`, pure: no clock, storage, AppState, or network; every function takes `now`): `start` (client-generated id and topic id stored in lowercase, planned minutes 1–1440, a snapshot of the session rules), `pause`, `resume`, `end` (each returns `{ ok, state }` or `{ ok: false, reason, state }`: `already_paused`, `not_paused`, `finished`, `time_went_backwards`, `invalid_time`), `settle(state, now)` (records a completion or pause-limit end at the instant it happened, however late), `derive(state, now)` (focused, paused, and remaining milliseconds, progress, `completionAt`, `pauseLimitAt`, `endedAt`, `reachedMinimum` as a preview only), and `toSubmission(state)` (the raw `PUT /me/sessions/:id` payload; the same state always gives the same payload). State is plain JSON with epoch-millisecond instants. Semantics match the API evaluator (A2.4): half-open pauses, completion at the instant focus reaches the plan (>=), the pause limit only once a pause goes past the maximum (>), the first of the two wins.
- **Active timer persistence** (`src/timer/active-timer-store.ts`, `ActiveTimerProvider`): `ActiveTimerStore` keeps the signed-in user's one timer (active, or finished and not yet handed off; only `clearFinished(id)` removes it: a finished timer with that id, storage first, then memory) under `focus-forest/active-timer/v1/<userId>` in AsyncStorage. Every successful transition (start, pause, resume, end, and a `refresh` or refusal that settles an end) is written, and memory changes only after the write succeeds; a failed write answers `storage_failed` with the previous state. No writes on ticks. `activate(userId)` reads, validates with `parseTimerState` (zod shape, then a replay through the engine that must give the same state back), settles at `now`, and stores a settled end before exposing it. A corrupt or other-version entry is copied to `…/quarantine`, removed, reported by code only (`report`), and treated as no timer. An unreadable storage makes the status `unavailable`, so nothing can start over a timer that may exist. `start` is refused while any timer exists (`timer_exists`). Sign-out only forgets it in memory. A clock that moved backwards makes actions answer `time_went_backwards` and nothing is written; no timestamp is ever invented. The root layout creates it (`createAppTimerStore`: AsyncStorage, `Date.now`, `createClientId`) and `ActiveTimerProvider` activates it for the signed-in user; read it with `useActiveTimer()`. Nothing listens to AppState yet (`refresh()` is for the foreground).
- **Topics data** (`src/api/topics.ts`, `src/topics/`): `topicSchema` (A2.2/A2.8: lowercase UUID, `topic.1`–`topic.12`, ISO times, `archivedAt` set exactly when archived, `lastUsedAt` and `lastPlannedMinutes` nullable), `listTopics(filter)` (`status`, `sort: 'recent'`), `createTopic(id, fields)` (`PUT`, caller's lowercase id), `updateTopic`, `archiveTopic`, `restoreTopic`, and `topicErrorCode` (`topic_name_taken`, `topic_id_conflict` from the 409 `code`; `HttpError.code` carries any API error code, branch on it and the status, never the message). Hooks: `useTopics(filter)`, `useRecentTopics()` (`status=active&sort=recent`), `useCreateTopic`, `useUpdateTopic`, `useArchiveTopic`, `useRestoreTopic` (online only; no offline queue until M2.5). Query keys `['me', 'topics', '<status>:<sort>']`. A mutation's answer replaces the topic in every cached list it belongs to and leaves the others (a create is appended, which is the server's order for a new topic), then every topic list is refetched, so order always comes from the server. `TopicSnapshotStore` saves each list the server answered under `focus-forest/topics/v1/<userId>` (a read cache, never the source of truth), and `TopicCacheProvider` loads it into the query cache before the first request, with `dataUpdatedAt` set to when the server confirmed it; `fromDeviceCache` tells the saved list from a fresh answer. Corrupt snapshots go through `readStoredJson` (`src/common/stored-json.ts`, shared with the timer): quarantined, removed, reported by code.
- **Offline topic creates** (`src/topics/topic-create-queue.ts`, `topic-create-sync.tsx`): `TopicCreateQueue` keeps the signed-in user's creates under `focus-forest/topic-create-queue/v1/<userId>` as `{ id, payload, state, attempted, queuedAt }`. `enqueue(fields)` canonicalizes once (`canonicalCreatePayload`: NFC, trimmed, blank description as null, like the API compares creates), takes a lowercase id, stores the item before answering, then flushes. `flush()` is single-flight per user, oldest first: each create is stored as `attempted` before it is sent, and from then on only ever resent with the exact same payload. Outcomes: 201/200 → `confirm` puts the topic in the cached and saved lists (`applyServerTopic`) and the item leaves the queue only if that was stored; network, 401, 5xx → stays pending and frozen (network and 401 stop the flush); 409 `topic_name_taken` → `needs_name_change` (nothing was created, so `revise(id, fields)` may change it, same id); `topic_id_conflict`, other 4xx, an invalid response → `needs_attention`, kept, never retried automatically. `revise` is refused (`not_revisable`) after an uncertain attempt. `isTopicSynced(id)` is false while any create for the id is queued or the queue is not known. Queued topics never enter the snapshot of confirmed lists. A synced create is kept first as an `unlisted` confirmed topic in the snapshot (`rememberUnlisted`: the exact PUT answer, with the time it was confirmed), so it survives a kill and an offline relaunch even when no list was ever fetched; the queue lets go only after that write. The saved lists stay exact server answers: an `unlisted` topic is dropped once the saved `active:recent` list has it, or was asked for strictly after it and lacks it (no longer active); list answers are saved with the time the request began, and an answer to an older request never replaces a newer saved list. `usePickerTopics()` returns the recent server topics, then active `unlisted` ones not in that list (creation order), all `kind: 'confirmed'`, then the queued ones (`kind: 'pending'`, with no server fields); each id once. A corrupt queue is copied to its quarantine key and removed only once the copy is kept (`readStoredJson(…, { removeOnlyIfKept: true })`). `TopicCreateQueueProvider` activates it and flushes at launch and sign-in; nothing listens to connectivity or AppState yet. Edit, archive, and restore stay online only.
- **Session outbox** (`src/api/sessions.ts`, `src/sessions/`): `submitSession(id, body)` (`PUT /me/sessions/:id`, answer validated by `sessionSchema`: the A2.5 session, whose `endedAt` is the server's effective end), `sessionSubmissionBodySchema` (the body exactly as `toSubmission` writes it: lowercase topic UUID, UTC instants with milliseconds, planned 1–1440, pauses in order and inside the session; no evaluation), `sessionErrorCode` (409 and 422 codes). `SessionOutbox` keeps the signed-in user's finished sessions under `focus-forest/session-outbox/v1/<userId>` as `{ id, payload, state, reason, queuedAt }`; the payload is stored once and sent unchanged on every attempt, never rebuilt and never replaced by a response. `enqueue(userId, submission)` answers a replay for the same id and payload and refuses another payload under a queued id (`id_conflict`). `flush()` is single-flight per user, oldest first; a session whose topic is not synced (`isTopicSynced`) first asks the topic queue to flush (once per flush), then is marked `blocked_topic` and skipped. Outcomes: 201/200 with the same id → the answer is first kept as its completion receipt (`keepReceipt`; not kept → the session stays queued, unchanged, and the next flush replays it), then removed only once that is stored, then kept in memory as `synced[id]`, and `onSynced` is called (also for a 200 replay, and even when the removal could not be stored, since the server has it; never for any other answer, nor after a user switch). The app wiring (`createSessionOutbox`) uses it to `invalidateTopicLists` (`src/topics/query-keys.ts`): a session changes the topics' `lastUsedAt`, `lastPlannedMinutes`, and recent order (A2.8), so the lists on screen are refetched and saved as usual; nothing is derived locally, and a failed refetch leaves the last saved lists. The removal never waits on it; network, 401 → kept, flush stops; 5xx → kept, next one; 422 `ends_in_future` → `pending`, resent unchanged later; 404 → `blocked_topic`; 422 `timezone_required` → `blocked_timezone` (retried every flush; nothing sets the time zone yet); 409 `session_overlap`, `session_id_conflict`, other 422s and 400s (`rejected`), an invalid response (`invalid_response`) → `needs_attention` with that `reason`, kept, never retried automatically. `handoffFinishedTimer({ timers, outbox })`: refresh (stores a settled end), `toSubmission`, enqueue, and only then `clearFinished`; a repeat after a kill or a failure at any step dedupes by id and payload. `SessionOutboxProvider` (inside the timer and topic-queue providers) activates it, hands off a finished timer at launch and whenever one finishes, and flushes when the outbox and topic queue are restored, after a handoff, and when the queued topics change. A corrupt outbox is quarantined and removed only once the copy is kept.
- **Topics screen** (Profile → Topics, route `src/app/(tabs)/profile/topics.tsx`; `src/topics/TopicsScreen.tsx`, `TopicSheets.tsx`, `topic-form.ts`): `Active` / `Archived` chips; `useManagedTopics(status)` gives the server list for that status (creation order, never sorted locally) plus confirmed `unlisted` topics, and for active the queued creates after them. Create asks only for a name (`NEW_TOPIC_DEFAULTS`: icon `topic.default`, color `topic.1`, description null; fixed, never derived) and closes once `enqueue` has stored it, online or not; a storage failure keeps the form and its text. `topicNameError` (blank; over 100 characters after trim and NFC) and `topicDescriptionError` (over 500) check only what helps while typing; the server decides duplicate names. A queued create shows under its name as `pendingTopicStatus(item).label` ("Waiting to sync", "Choose another name to sync this topic.", "This topic needs a look before it can sync."), never an internal code; it opens a revise form only while `editable` (never sent, or `needs_name_change`: same id), otherwise a read-only explanation. A confirmed topic opens `EditTopicSheet`: name, description, and `Color 1`–`Color 12` chips (label plus selection, never color alone); `topicChanges` sends only changed fields and never the icon; online only, so a failed save keeps the sheet and the cached topic; `topic_name_taken` is a field error. Archive (from the edit sheet) asks first ("Your past focus sessions will stay in history."); archived rows have a one-tap `Restore <name>` (a `topic_name_taken` answer says an active topic has the name and renames nothing). A failed list with saved data shows `InlineStatus` "Showing topics saved on this device."; with none, `ErrorState` and a retry. No icon picker until the curated icon set exists. `Button` takes an optional `accessibilityLabel` that must contain its label, for repeated labels such as `Restore`.
- **Duration** (`src/focus/duration.ts`, `DurationSheet.tsx`): whole minutes only. `DURATION_PRESETS` 15 / 25 / 45 / 50 / 60 (docs/02), `FIRST_SESSION_MINUTES` 15, and a custom range of 5–180 minutes in 5-minute steps (`isSelectableDuration`; a mobile product choice, narrower than the API's 1–1440). `initialDurationForTopic(pickerTopic)` opens with the confirmed topic's `lastPlannedMinutes` (the server's remembered duration, A2.8) when the selector can show it, otherwise 15: a topic never used, one waiting to sync, or a remembered value outside the range (never clamped or rounded). `parseCustomMinutes` refuses anything else with a calm message. `DurationSheet` (`initialMinutes`, `confirmLabel`, `onConfirm(minutes)`, `onCancel`) shows the presets and `Custom` as `Chip`s (named by their minutes, selection by outline) and a `Minutes` number field in custom mode; it restarts from `initialMinutes` at every opening, and starts and stores nothing: the remembered duration only changes when a session with it syncs. `formatMinutes` writes "25 min".
- **Duration with the session minimum**: `isSelectableDuration(minutes, minimum)`, `parseCustomMinutes(text, minimum)`, and `DurationSheet minimumMinutes` add the session rules' `minValidMinutes` (a shorter plan would never count): presets below it stay visible but disabled, custom minutes must reach `lowestSelectableMinutes(minimum)` (the first 5-minute step at or above it; the rule itself is never rounded; null above 180, `NO_DURATION_MESSAGE`). `quickStartMinutes(entry, rules)` is the confirmed topic's remembered duration when it is offered under the minimum, else null; `startMinutesForTopic(entry, rules)` opens the choice on that, else 15, else the first preset (or step) that meets the minimum, else null.
- **Session rules** (`src/api/session-rules.ts`, `src/focus/session-rules.ts`): `getSessionRules` (GET `/session-rules`, `sessionRulesSchema`: whole numbers ≥ 1 and the configuration `version`). `useSessionRules()` gives the server's answer and saves it under `focus-forest/session-rules/v1` (one key: the rules are the same for everyone); until the server answers, the saved rules stand in (`fromDevice`), so a cold offline launch can still start (docs/07 §4). Without either it is `unavailable` and nothing starts: 5 and 30 are never assumed. The server evaluates submissions with its own rules anyway.
- **Start Focus** (`src/focus/StartFocus.tsx` under the Home hero; route `src/app/focus.tsx` outside the tabs): with a running or paused timer the button reads `Resume focus` and reopens it, never replacing it; a finished one is handed to the outbox first (`useFinishedTimerHandoff`), and if that cannot be stored nothing starts. The topic sheet lists `usePickerTopics()` in its order (queued topics with `pendingSyncLabel`); a topic with a `quickStartMinutes` starts at once (two taps from Home) and has a separate `Change duration for <name>` button; others open `DurationSheet` (`Start focus`). Rows are disabled while the rules load, when they are unavailable, or when no duration meets the minimum. `timers.start` gets the topic id (a queued topic's own id: the outbox waits for its sync), the minutes, and a copy of the rules; the Focus route opens only after the timer is stored, and a storage failure keeps the sheet with a calm message. No topic yet: `Create topic` reuses `CreateTopicSheet`. Nothing about durations is stored.
- **Focus screen** (`src/focus/FocusScreen.tsx`): shows the stored timer, never its own. `useWallClock(timers.now)` reads the store's clock about once a second in the foreground (and on return); the view is `derive(timer, now)`, formatted by `src/focus/countdown.ts` (display only). The progress ring gets `ringPercent` (whole focused minutes), so it animates once a minute, not on every tick. When the view says the session ended, the screen calls `timers.refresh()` so the end is stored at C or L. Pause, Resume, and End call the store and show only what it stored; a failure or `time_went_backwards` shows a calm status. End asks first (`Confirmation`, modal); back asks the same (`beforeRemove`), and the native swipe is off on the route. The countdown is never a live region: a `Time left` button reads it aloud on request (`spokenTimeLeft`). Topic name and mark come from `useTopicIdentity` (saved lists, unlisted, or the queued create), else `Focus topic`. A finished timer shows `Saving your session.` while `useFinishedTimerHandoff()` runs, a retry if it cannot be stored, then a minimal finished state (`Session complete` or `Focus session ended`, focused minutes, Done): the Session Completion contract (M2.12) is the session id, looked up in the outbox `items` or `synced`.
- **App lifecycle:** `ActiveTimerProvider` refreshes the timer whenever AppState becomes `active`, so an end reached in the background is stored at its instant on any screen; the provider's handoff then queues it. Nothing runs in the background. `SessionOutboxProvider` runs one handoff at a time; `useFinishedTimerHandoff()` shares it.
- **Timer notifications** (`src/notifications/`, M2.10): `TimerNotificationCoordinator` follows the timer store and plans the one notification the stored timer needs with `derive` (completion at C while running, pause limit at L while paused, none once ended), then brings the OS in line: it cancels this user's other timer notifications and schedules the plan under `focus-timer.<session id>`. Runs one at a time, latest state wins; it only touches the current user's notifications. Permission is asked just in time, the first time a timer needs a notification, once per launch and only while the OS may ask; refused, the timer runs the same. Failures are reported by code (`schedule_failed`, `cancel_failed`, `read_failed`, `permission_failed`) and repaired on the next run; they never touch the timer. `ActiveTimerProvider` calls `onForeground` (the coordinator) after its foreground refresh. `expo-timer-notifications.ts` is the only file that imports `expo-notifications`: two stable Android channels (`focus-timer` with the default sound, `focus-timer-silent` with `sound: null`, same importance; a channel's sound cannot change once created, so the preference picks the channel), no notification handler (the OS default keeps them off screen while the app is open). The `sound` preference is the content's `sound` on iOS and the channel on Android; a change reschedules the pending one. No exact-alarm permission in Phase 2: Android may deliver late in Doze, and the timer's truth is its timestamps either way. Sign-out cancels nothing: the signed-out user's timer is still stored, so its notification stays; a notification tap (M2.12) must check the notification's `userId` against the signed-in user. Tests use the in-memory OS in `src/test-utils/notifications-mock.ts` (jest-setup mocks the module).
- **Foreground wake-up** (`src/timer/foreground-wakeup.ts`, in `ActiveTimerProvider`): while the app is active and a timer runs or is paused, one `setTimeout` waits for C (or L + 1 ms: a pause ends once it goes past L); waking only calls `timers.refresh()`, so the end is stored at the engine's instant however late it wakes. It follows every stored change and the existing AppState listener (off in the background). `onForeground` (root layout) then reconciles the timer notifications and retries the session outbox, then the note queue.
- **Session Completion** (`src/completion/`, route `src/app/completion/[sessionId].tsx`, outside the tabs): resolves the session from its completion receipt, the note queue's `confirmed`, or `outbox.synced` (the server's evaluation: status and `focusedMilliseconds`; the receipt is written before the other two, so it is never older), else the history item (see Focus history), else the queued submission (`focusedMillisecondsOf`, the device's measure, titled `Focus session finished` with no outcome claimed), else `Saving your session.` while stores are read or the timer is being handed off, else `This session isn't on this device.` Titles: `Session complete` (completed), `Focus session saved` (ended early; discarded adds the minimum explanation). The outcome is announced, again if the server's answer changes it. No tree, goals, or streak (Phase 3+).
- **Which Completion opens** (`CompletionIntents`, `CompletionNavigator`): a session this launch saw running or paused, once handed off (or Focus's own handoff), opens from Focus (replacing it) or Home, and otherwise waits until the user is back on Home; a tapped timer notification (`onTimerNotificationTap`, including the launch tap) opens it from anywhere. Only for the signed-in user: another user's request is dropped. Each session opens at most once per launch.
- **Session notes** (`SessionNoteOutbox`, `SessionNotesProvider`, key `focus-forest/session-notes/v1/<userId>`): Save note and Done store the canonical note (A2.6: NFC, trimmed, blank is null, at most 500 code points; `session-note.ts`) on the device before anything else; Done never waits for the network. A note is sent (`PATCH /me/sessions/:id/note`) only once its session is confirmed (`sessionConfirmedOnServer`): not while the timer still holds it, not while it is in the outbox, and yes once it has left the read outbox (which happens only after a validated PUT answer), the same value until answered, and removed only when that very revision is confirmed. 5xx and 404 retry; offline and 401 stop the run; a 400 or a malformed answer keeps it as `needs_attention`. The note never goes into the session submission. A confirmed note's answer is kept as the completion receipt before the note leaves the queue (not kept → it stays queued and is sent again). Completion shows a queued note over the receipt's. A `needs_attention` note shows `This note is still saved on this device and needs attention before it can sync.`; saving an edit makes a new pending revision, which is sent again.
- **Completion receipts** (`src/sessions/completion-receipts.ts`, `CompletionReceiptsProvider`, key `focus-forest/completion-receipts/v1/<userId>`, `{ version: 1, receipts: FocusSession[] }`): the server's validated answers (PUT, PATCH …/note) for the user's 20 most recent sessions, oldest first by first confirmation; a newer answer replaces its receipt in place, the 21st evicts the oldest (`COMPLETION_RECEIPTS_MAX`, a technical cache bound). It lets Completion open by id after a restart (a tapped notification for a session synced earlier): the API has no lookup by id. A read cache, not history: never a note waiting to be sent, never fetched from history. `keep` waits for the read, writes before showing. A corrupt entry is quarantined, then removed, and the cache starts empty; the timer and the queues never read it.
- **Focus history** (`src/api/history.ts`, `src/history/`, Insights tab, docs/05 §1–§3): `getSessionHistory(client, { cursor })` (`GET /me/sessions?limit=30[&cursor]`, `HISTORY_PAGE_SIZE` = the API default; the cursor is passed back as given, never read), answers validated by `historyPageSchema` (each item: the A2.5 session fields plus `topic` {id, name, icon, color, status} as it is now). `useSessionHistory()` is a TanStack infinite query (`historyQueryKey`); the next page loads only on `Load more sessions`; pages are merged in order, each id once (`mergeHistoryPages`). Rows are grouped by the persisted `localDate` in first-occurrence order, rows in server order (`groupByLocalDate`: never recomputed from `startedAt`, never sorted); day labels format the date-only value in UTC (`formatLocalDate`, no Today/Yesterday: the device's today may not be the user's). A row shows the history item's own topic summary (never the topic cache), start time (device clock), `outcomeLabel` (`Completed`, `Ended early`, `Not counted` from the server's `counted`), and `formatFocused(focusedMilliseconds)`. Offline: `HistorySnapshotStore` (`focus-forest/history/v1/<userId>`, `{ version: 1, savedAt, items }`, at most 100, a read cache, quarantined when corrupt) is written inside `queryFn` (a first page replaces it, a next page is added); it is shown (never paged) until the server answers, with `Showing history saved on this device.` when the server cannot be reached. A synced session invalidates the history (`onSynced`, with the topic lists); nothing is shown before the server lists it. A row opens `/completion/[id]`: Completion falls back to the loaded or saved history item (`useHistoryItem`, no fetch, no receipt needed), and uses its topic summary when the topic cache does not have the topic.
- **Timer tests with a clock:** route tests move `deviceClock.now` (`src/timer/app-timer-store.ts`), never `Date.now`, which React Native's `Animated` keeps time with. `mockAppState()` (`src/test-utils/app-state.ts`) sends the app to the background and back. Route tests that land on Focus serve `reducedMotion: true`, so the progress ring's JS-thread animation never runs its frames between test steps.
- **Route tests with sheets** use `until` and `settleSheetTransitions` (`src/test-utils/sheets.ts`): wait for a closed sheet to leave inside act, since the native animation mock ends transitions on real timers. Typed routes (`.expo/types/router.d.ts`, generated and ignored) are regenerated with Expo Router's own generator when a route is added; no dev server is needed for it.
- **Client ids** (`src/ids/client-id.ts`): `createClientId()` returns a lowercase UUID from `expo-crypto`.
- The pure timer files (`timer-engine.ts`, `submission.ts`, `timer-state-schema.ts`) may not import storage, `expo-crypto`, React, or React Native (lint).
- `npm run check` runs typecheck, lint, format check, and tests. `npm run doctor` runs `expo-doctor`.

## Known issues

- **Route tests that sometimes time out under load.** `navigation.test.tsx`, `settings.test.tsx`, and `profile.test.tsx` occasionally fail one test with the launch screen still on top (`accessibilityElementsHidden`), after 30–50 s, when the machine is busy; a rerun passes. Reproduced on the Phase 1 baseline without Phase 2 code. Not yet investigated: start by timing the preferences wait in `renderApp` with `--runInBand` against the default workers.
